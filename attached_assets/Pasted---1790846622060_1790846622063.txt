52. Prompt للـAI — Failure
You are the adaptive habit coach.

The application has already determined:
- current target
- current minimum
- recent performance
- failure reason
- recommended adjustment

Do NOT change any numeric value.

Your job is to:
1. explain what happened without blame
2. explain the recommended next step
3. encourage the user
4. suggest one practical action

Failure reason may be:
- too_difficult
- no_time
- forgot
- lost_motivation
- unexpected
- other

For:
too_difficult:
Explain that reducing friction or target can help.

no_time:
Suggest a smaller busy-day version.

forgot:
Suggest attaching the habit to an existing routine/cue.

lost_motivation:
Suggest making the starting action smaller/easier.

unexpected:
Treat it as an exception and avoid unnecessary changes.

Never shame the user.
Never diagnose.
Never claim scientific certainty.
Return concise natural Arabic.
Return structured JSON.
53. Prompt — Daily Coach
You are the daily coach inside a personal habit application.

Possible context:

Do not invent behavior.

55. Prompt جاهز لـReplit

هذا هو النص الذي أعطيه الآن لـReplit:

Implement Feature 04:
DAILY HABIT EXPERIENCE + CHECK-IN + CONSISTENCY + FAILURE/RECOVERY UX

IMPORTANT:
Do not redesign unrelated features.
Do not remove existing Habit Creation, AI Coach, Time Tracking, Journey, XP, Coins, or Reward functionality.
Inspect the current implementation first.
Reuse current components, APIs, database tables, and rules whenever possible.
Implement this feature incrementally.
Do not replace the existing system from scratch.

==================================================
1. DAILY HABIT HOME
==================================================

When a user opens the application, the primary screen should answer:

1. What do I need to do today?
2. What is the target?
3. What is the minimum?
4. How much have I completed?
5. Where am I in the journey?
6. What am I working toward?

Show:

- Habit name
- Today's target
- Today's minimum
- Current progress
- Journey day
- Consistency
- Reward
- Start/Complete action

Make "minimum" visually reassuring.

Example:
Target: 10 min
Minimum: 5 min

Use Arabic RTL.

==================================================
2. SUPPORT HABIT TYPES
==================================================

Support existing habit types where the current data model allows:

BUILD duration habit
BUILD count habit
BUILD boolean habit
REDUCE habit

For BUILD:
actual >= minimum → successful day
actual >= target → target achieved

For REDUCE:
actual <= success limit → successful day
actual <= target limit → target achieved

Do not treat minimum achievement as failure.

==================================================
3. HABIT EXECUTION
==================================================

Duration habits:
- Start
- Pause
- Resume
- Finish

Use timestamps as the source of truth for elapsed duration.
Do not rely only on a visual frontend timer.

Count habits:
- plus/minus controls
- current count
- target count

Boolean habits:
- simple completion action

Reduce habits:
- show current usage
- target limit
- success threshold
- progress

==================================================
4. PARTIAL COMPLETION
==================================================

When:
minimum <= actual < target

Show:
"Minimum reached."

Then ask:
"Continue or finish for today?"

Buttons:
- Continue
- Done for today

Minimum completion counts as a successful day.

==================================================
5. TARGET COMPLETION
==================================================

When actual >= target:

Show:
"Target complete."

Trigger:
- XP
- Coins
- journey progression
- character movement
- consistency update

Do not automatically increase tomorrow's target.

==================================================
6. OVERACHIEVEMENT
==================================================

If actual > target:
- show recognition
- optionally award a small bonus if existing economy supports it
- do not automatically set tomorrow's target to the achieved value
- allow future adaptation through the existing rules engine

==================================================
7. DIFFICULTY CHECK-IN
==================================================

After completion ask:

😊 Easy
😐 Normal
😣 Hard
😞 Very Hard

Optional note field.

Persist difficulty using the existing data model where possible.

If the current system stores numeric values internally, map them cleanly to these four user-facing states.

Do not break historical data.

==================================================
8. CONSISTENCY
==================================================

Do NOT center the experience around traditional streak language.

Use:

"6 successful days out of 7"

Calculate this deterministically.

Successful day:
BUILD → actual >= minimum
REDUCE → actual <= success limit
BOOLEAN → completed

A missed day must not reset the entire journey.

==================================================
9. USER DID NOT COMPLETE THE DAY
==================================================

When the day expires without successful completion:

Show:

"Yesterday didn't go as planned."

Then:

"What got in the way?"

Options:

- Too difficult
- No time
- Forgot
- Lost motivation
- Unexpected event
- Other

Persist the real selected reason.

Do NOT hard-code missedDays = 1.

Use actual habit history.

==================================================
10. FAILURE ADAPTATION
==================================================

Pass failure reason into the existing deterministic adaptation engine.

Rules:

Too difficult:
→ reduce future target/minimum gradually

No time:
→ offer Busy Day Version
→ do not automatically reduce main target

Forgot:
→ suggest cue/reminder adjustment

Lost motivation:
→ simplify starting action / reduce friction

Unexpected:
→ normally keep the plan

One difficult day should not cause a major target reduction.

Repeated difficulty can trigger adaptation.

==================================================
11. BUSY DAY VERSION
==================================================

Support:

Normal target
Minimum
Busy-day version

Example:

Target = 10 min
Minimum = 5 min
Busy-day version = 3 min

When user reports "No time", show the smaller option.

Do not permanently replace the main target.

==================================================
12. CUE ADAPTATION
==================================================

For "Forgot":

Allow:
- fixed time
- existing routine cue
- custom cue

Example:
"After morning coffee"

Do not invent routines that the user has not provided.

==================================================
13. FAILURE AI
==================================================

Use the AI only to explain and coach.

The deterministic engine decides numeric changes.

AI receives:
- failure reason
- recent history
- current target
- new target if changed
- recommended action

AI must NOT modify the numbers.

Return concise Arabic structured JSON:
{
  "headline": "...",
  "explanation": "...",
  "next_step": "...",
  "encouragement": "..."
}

If AI fails, use a deterministic Arabic fallback.

Never show technical API errors.

==================================================
14. OPTIONAL RECOVERY — LITE
==================================================

If the existing codebase can support it without destabilizing V1, implement a lightweight consistency recovery system.

Limit:
2 recovery opportunities per journey.

Flow:
Missed day
→ Reflection
→ Recovery available
→ User chooses recovery
→ Show small recovery challenge
→ Complete challenge
→ Mark missed day as recovered
→ Update consistency

Do NOT make recovery punitive.

Example:
Normal target = 10 min
Recovery challenge = 15 min

Do not require huge tasks.

Track:
recovery_used
recovery_limit = 2
recovered

If recovery challenge is not completed:
do not allow unlimited retries.

If implementing Recovery would destabilize core functionality, leave it disabled but keep the architecture ready.
